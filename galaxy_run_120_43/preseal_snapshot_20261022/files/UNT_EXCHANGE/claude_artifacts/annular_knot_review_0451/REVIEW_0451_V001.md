## Notes (not defects)

1. **Changed meanings, documented in the interface:**
   - `arrays['radial_derivative']` is now the 72x19 dB/dR, where v001 had a 72x72 nodal operator. It means the same thing but has a different shape. A consumer expecting 72x72 fails loudly, not silently.
   - The `lower_surface_trace` and `upper_surface_trace` rows are kron(B, ·), 72x152. This is the same formula as v001's kron(I, ·), since v001's B was the identity.
   - V is not block diagonal. The 0438 projection must not be used with these maps; root uses Gkin.
2. **Custody.** `old_scalar_map_sha256` and `binding_module_sha256` are caller assertions compared with the pins, the same pattern as v001. The module also checks the integrity of the old maps exactly: the Legendre blocks of the stored zeta, the stored root derivatives against the stored operator, and the weight sums.
3. **Scope of the correction.** Within each annulus every cardinal B_j is a single cubic in s, so 4-point Gauss-Legendre in s integrates the purely polynomial scalar products exactly. That removes the knot-inside-group cause of root's measured radial scalar defect. Several factors remain non-polynomial in s: the preserved v001 geometry slopes (from the 72-knot spline), the regularity powers s^(e/2) for odd e, sqrt(s) inside d_R, and the physical fields. The correction therefore cannot make every fluid integral exact, and it does not establish convergence or resolution adequacy, as the contract itself states.
4. **Environment.** Under Python 3.9.6 with numpy 2.0.2, numpy prints spurious "divide by zero / overflow / invalid value encountered in matmul" RuntimeWarnings. The pinned v001 helicity module triggers them too. All values are finite, the module's own finite() guards would otherwise raise, and every check passes. The root interpreter (3.12 with numpy 2.3.5) prints no such warnings.
