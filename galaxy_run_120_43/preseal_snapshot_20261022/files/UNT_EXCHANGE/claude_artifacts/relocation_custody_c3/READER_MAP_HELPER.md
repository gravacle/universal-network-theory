## E. `storage_check move` - exact behaviour
- Arguments `--candidate DIR --work-dir WD --pins-from F (repeatable) [--follow]` (STORAGE L156-160).
- `cand = os.path.realpath(a.candidate)` (L111); not a directory -> prints NOT_MOVABLE with reason "candidate is not a directory: <cand>" and exits 3 at once (L112-114).
- `wd = os.path.realpath(a.work_dir)` (L115). Pins = every `{path, sha256(64)}` anywhere in each --pins-from JSON (L98-107). With --follow, a pinned `.json` <= 8 MiB is opened for its own pins up to depth 3 (L131-133), except NO_FOLLOW paths `/runs/ /runs_ext/ unt_internal_runs /volumes/ ngc3198 c5h /.codex/ /uvt_` (L37, L40-41), whose pins are compared by path only.
- Refusal reasons (all collected, then status NOT_MOVABLE, exit 3; L139-141): "pin source unreadable: P (ExcType)" (L126); "pinned by SRC: Q" for every pin whose realpath equals the candidate or lies under it (L134-135); "the campaign work dir WD is or contains or is inside the candidate" when `wd == cand or wd.startswith(cand + '/') or cand.startswith(wd + '/')` (L136-137). Stated rationale: "the cache re-hashes entries by path, parent L2302-2341; SF1 pins the work dir identity" (L19-20).
- Allowed: prints `{schema H3_STORAGE_MOVE_CHECK_C2V001, candidate, work_dir, pin_sources_read, n_pins, status MOVABLE, reasons []}` and exits 0 (L138-141). It moves nothing; the move is root's: "ditto, then a sha256 manifest of both trees compared equal, then the source removed; never a plain mv across volumes" (L21-23).
- Consequence: every campaign call dir is `<WD>/waves/.../call_%04d`, so `cand.startswith(wd + '/')` always holds and `move` ALWAYS refuses a call dir. Edge: if a call dir is ALREADY a LINK to External1, `realpath(candidate)` lies outside WD and only the pin rule can refuse; cache entries and other JSON under /Volumes are never followed (NO_FOLLOW `/volumes/`), so their pins are seen only when passed directly with --pins-from.

## G. Facts that constrain any relocation design (no proposal made)
1. Absolute call-dir paths sit in sha-pinned bytes at three levels: files inside the call dir (A3), cache entries that are never overwritten (A2; ORCH L2471-2476), and records-dir acceptance records with RESOLVED paths (HANDOFF L341-368, L411). A relocation cannot rewrite any of them in place.
2. The generic VALID-entry checks (B2, B3) compare realpaths on both sides or reuse the recorded strings, so a LINK keeps them passing in the code read here; every `resolve()`-based check (B4, B5, B9, the second acceptance pass in B10) and every RB/G26 realpath-normalised check (B12) refuses a LINK. A MOVE with nothing at the old path is refused by every verifying reader (STORAGE wave only stops counting it; an interrupted-wave resume would relaunch it).
3. No reader records or checks the volume, VolumeUUID, st_dev or inode of a call dir: only of the WD (ORCH L631-718, L3022-3061) and of RB run volumes (RB L3283-3290, L5345-5346). Volume custody for relocated call dirs would be a new check. The nearest existing precedent is RB G16 custody: copies under a custody root, byte-equal, with a distinct (st_dev, st_ino), an exact required set, and restore rather than reinterpret (RB L5336-5385, L3369-3440).
4. Any config edit changes config_sha256, so ENTRY and ACCEPT refuse every existing wave (ENTRY L148-151, ACCEPT L164-166). Any edit inside tail_readiness also changes cache_id, so the C4-2 refusal hits every command (WRAP L136-139; ORCH L3094-3100).
5. Interrupted-wave resume relaunches an absent call dir (CAMP L175-185 -> L207-215). Uncommitted waves (WAVE_PLAN without WAVE_RESULT, ORCH L3468) must never be relocation candidates.
6. `storage_check move` refuses every campaign call dir by construction (STORAGE L136-137). A relocation path for call dirs needs a successor tool or rule, not this check.
7. One F6 (TAIL_ACCEPTANCE_CERTIFIED) entry whose call dir is MOVED or LINKED makes every Cache.open refuse, i.e. plan, run, status, resolve, reingest and accept all stop (B5, WRAP L547-552).
