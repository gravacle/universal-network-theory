### 2. N>1 bitwise equal to serial — PASS
- **Column order.** `begin_iteration` queues the fresh columns `len(restored)..n-1` in roster order (D127–128, D719–725); `_dispatch_columns` pops them in order within a 16·N look-ahead and ≤2 in-flight tasks per worker (D732–744); `take(column_index)` refuses any index other than `next_take` (D753) and blocks until that index's result exists (D754–758). Consumption is therefore strictly in column order through the reviewed `try` (D133–144), and the reviewed `write_column`, `column_completed` and J accumulation statements are untouched.
- **HI ValueError semantics.** The worker wraps exactly the same `solve_hi_column` call (D480–486; AST-identical to the serial call, and `metric_point`/`at_z` are AST-identical to the serial closures, with `args['Cbar']`, `args['mubar']`, `c_m_s`, `reality_*` shipped by value). The parent re-raises inside the reviewed `try` with the worker's `type(exc).__name__` and `str(exc)` (D561–584; a non-transferable ValueError subtype is re-created under its own name as a ValueError subclass), and the reviewed failure record uses only those two (base L171). Because `take` is in-order, the first failing column in column order wins; look-ahead results for later columns are never written or announced (D753–766), and the pool is closed in `solve`'s `finally` (D72–75).
- **Worker assignment.** Results are keyed by column index; per-column worker state is a fresh line cache (D451–466), equivalent to the serial cache because `prepare_line` is a pure function of `(prepared, x, y)`; no HI-side module has a module-level cache (grep of the five LOCAL HI/line/facade/quadrature modules: none).
- **Own synthetic evidence** (author's problem builder, reviewed helper modules): on an exhausted vertical case (8 columns, 2 iterations) and a converged non-vertical case, the reviewed solver and the parallel solver at N=1, 3, 4 and a repeated N=3 give identical outputs and identical progress-event streams under an alias-insensitive canonical digest (values, dtypes, shapes, key order). Failure case (metric-call budget at column 5): identical failure record (type, message, iteration 0, column 5), identical events, 5 completed columns in both. TypeError in column 2 propagates with the same type and message. Worker BLAS environments all report 1 thread.
- **Aliasing note (disclosed in the INTERFACE, confirmed).** A pickle-based digest of the raw output differs between serial and parallel because worker results are copies (no shared references with inputs); a structural walk finds no value, dtype, shape or key-order difference.

### 3. Source-transform split — PASS, no summation order can differ
- Gate (D801–816): file sha must be `81af8715…`, `physical_source_fourier.__code__` must equal the compiled file's function, kwdefaults must be `{wave_chunk: 64, source_chunk: 256}`, and the function's globals must be the module's. Otherwise the reviewed serial call runs (D156).
- Blocks (D612–620): `chunks = ceil(nk/64)`, `count = min(chunks, 3·N)`, edges `i·chunks//count` → every boundary is a multiple of 64 and every block is non-empty (count ≤ chunks); the last block ends at `nk`. Parts are concatenated in block (wave) order (D791–798); the first failing block in wave order is raised.
- In S194–207 each output row block `result[ka:kb]` is produced by its own wave chunk: `phase = einsum('kd,jd->kj', kv[ka:kb], pos[ja:jb], optimize=False)`, `term = einsum('kj,jfs->kfs', factor, src[ja:jb], optimize=False)`, `result[ka:kb] += term` over source chunks in order. With `optimize=False` numpy's einsum sums each output element over `j` sequentially, independently of how many wave rows are in the call, and the source-chunk accumulation order is the same in a sub-call. A chunk-aligned sub-call on waves `[a:b]` iterates chunks `[a+64m, a+64m+64)`, the same row sets as the full call, including the partial last chunk. Hence no floating-point operation or order differs across block boundaries. Own test (random nk=1000, ne=700): aligned blocks are bitwise equal to the full call, and so is a deliberately misaligned split (max |Δ| = 0.0) — the alignment guard is conservative rather than load-bearing for this einsum, and should be kept in case the contraction is ever BLAS-dispatched.

### 4. Determinism hazards — PASS with notes
- Spawn context (D622); BLAS/OMP/MKL/NUMEXPR/VECLIB thread variables set to 1 before `Process.start` and restored in `finally`, including deletion of previously absent keys (D623–636); workers echo their environment (D519) and the report records it.
- The worker bootstrap re-reads and re-hashes the solver file (D412–419) and the parent refuses to start if its own file changed since import (D609–611). Workers are daemons, ignore SIGINT (D492), and are stopped/terminated/killed in `close` (D646–662). Pool/transport failures are `ColumnPoolError` (RuntimeError), never a physical failure (D189–191, D574, D580–581).
- `module_patches`: plain-data globals and functions of file modules are replicated (D284–286, D360–370), functions only if their code object exists in the pinned file (D373–381). The v005 driver's patches set `SEED_SHA` and `IDENTITY` (plain values; driver L1635), so they hold in workers. Class-instance globals are not replicated (disclosed).
- Spawn re-executes the parent `__main__` under `__unt_parent_main__` with the main guard off (D274–276) and multiprocessing itself re-imports it as `__mp_main__`. Both worker successors and `galaxy_m0_forward_c2v005.py` have `__main__` guards. A caller without one fails loudly before any write (`POOL_START_FAILED … BrokenPipeError`), which my first harness reproduced.
- No per-column timeout: a hung worker blocks `multiprocessing.connection.wait` (D704) until the run's monitor wall cap; a crashed worker is detected via its sentinel and surfaces as `ColumnPoolError` with partial progress committed.
